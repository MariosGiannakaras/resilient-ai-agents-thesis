# Evidence — A Formal Verification Framework for Runtime Assurance

## Evidence E1 — Simplex RTA separates a high-performance controller from a trusted fallback
- **Type:** faithful paraphrase
- **Location:** Abstract; Section 1.1
- **Claim:** A Simplex runtime-assurance architecture allows an untrusted advanced controller to operate while a runtime monitor can hand control to a trusted reversionary controller when a safety condition is violated.
- **Thesis use:** fallback architecture
- **Topics:** runtime assurance; Simplex; fallback; monitor
- **Status:** verified

### Faithful paraphrase
The system contains an advanced controller that may be high-performing but not fully verified, a runtime monitor, and a trusted reversionary controller. The advanced controller operates while the monitoring condition remains acceptable; when the condition fails, the trusted controller takes over to preserve the required safety property.

### Limitation
The guarantee concerns the wrapped system under the stated monitor and fallback assumptions. It does not prove that the advanced learning controller itself is correct or resilient.

## Evidence E2 — An AI/ML controller can remain a black box inside a verified outer architecture
- **Type:** faithful paraphrase
- **Location:** Abstract; Sections 1–2
- **Claim:** The framework can be instantiated at levels of abstraction that leave the advanced controller partially unspecified while verifying system-level properties around it.
- **Thesis use:** verified-wrapper vs verified-agent distinction
- **Topics:** black box; formal verification; AI/ML controller
- **Status:** verified

### Faithful paraphrase
Plaidypvs can model the advanced component using only the interface properties or bounds needed by the proof. This makes it possible to reason formally about the RTA architecture without proving the internal implementation of an AI/ML controller.

## Evidence E3 — System safety depends on explicit handoff and fallback proof obligations
- **Type:** faithful paraphrase
- **Location:** Section 2; Formula (1); RTA proof rule
- **Claim:** The general RTA proof decomposes system safety into an initial safety condition, monitored advanced-controller obligations, a valid switch condition, and a trusted fallback obligation.
- **Thesis use:** safety-mechanism specification
- **Topics:** invariant; switch condition; recoverable state
- **Status:** verified

### Faithful paraphrase
The framework requires the system to begin in a safe state, the monitored advanced controller to preserve safety while the monitor permits it to run, and the state at handoff to satisfy conditions from which the reversionary controller can maintain the safety invariant. A fallback is useful only if intervention occurs while the system is still recoverable.

## Evidence E4 — Monitor sampling delay changes how early intervention must occur
- **Type:** faithful paraphrase
- **Location:** Sections 2–3; braking example, Equations (4)–(10)
- **Claim:** The proof explicitly accounts for how far the system can drift between monitor samples and derives a sampling/intervention condition that leaves enough margin for the fallback to act.
- **Thesis use:** intervention-latency metrics
- **Topics:** sampling interval; safety margin; detection delay
- **Status:** verified

### Faithful paraphrase
In the braking example, the switch condition must account for the worst motion that can occur before the next monitor sample. The reversionary controller therefore needs to be activated before the system crosses the point from which safe recovery is impossible.

### Thesis-safe implication
For a discrete GridWorld fallback, report monitor/intervention latency and whether the override occurred before entering an irreversible hazard state.

## Evidence E5 — Safe fallback persistence and successful return to the advanced controller are separate issues
- **Type:** faithful paraphrase
- **Location:** Section 2, switchback discussion
- **Claim:** The basic RTA formulation specifies switching to the reversionary controller but does not automatically guarantee when or whether control should return to the advanced controller.
- **Thesis use:** fallback dwell/switchback metrics
- **Topics:** switchback; fallback duration; hysteresis
- **Status:** verified

### Faithful paraphrase
A system can satisfy the safety invariant while remaining indefinitely under the reversionary controller. Returning control requires an additional monitored condition and extra assumptions. Safety alone therefore does not establish high-performance recovery or successful resumption of the learned policy.

## Evidence E6 — RTA recovery is not the same as learning-agent adaptation
- **Type:** thesis-safe inference from the architecture
- **Location:** Sections 1–4
- **Claim:** The RTA mechanism contains risk by switching controllers; it does not itself demonstrate that the advanced controller detected an environmental change, updated its policy, or relearned the task.
- **Thesis use:** safety/resilience boundary
- **Topics:** fallback; adaptation; detector
- **Status:** verified

## Avoid overclaiming
Use this source for a monitored safety-wrapper or fallback baseline and for intervention-timing assumptions. Do not describe system-level fallback safety as evidence that the learning agent itself recovered or adapted.
